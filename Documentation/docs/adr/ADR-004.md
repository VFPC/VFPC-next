# ADR-004 — Exit Point Validation Diagnostics and Warnings

- **Decision status:** Accepted
- **Acceptance recorded:** 5 November 2026, following project-owner approval of the draft ADR
- **Implementation status:** Implemented in working source; Debug and Release Win32 builds passed with zero warnings/errors; isolated checks and scoped user-operated Sweatbox scenarios SB01–SB07 passed, with final operator confirmations recorded on 6 November 2026; release publication remains separate
- **Record prepared:** 5 November 2026

## Context

vFPC needs to explain exit-point failures more precisely while preserving the existing validation rules. A known exit point that is not permitted for a filed departure differs from an unknown exit point. Where airport constraints support other departures, the diagnostic can help the controller identify a permitted alternative.

EuroScope exposes a filed route and an extracted waypoint list. The latter can include an intermediate exit point that is not explicitly written in the filed route. Finding that point in the extracted list does not itself prove that it is permitted for the filed departure or that every other route constraint is satisfied.

The agreed approach preserves checkExitPoint and the existing use of row.extracted_points, preserves route validation, and adds WRN when a permitted exit is extracted but not explicitly filed.

## Decision

### Preserve validation behaviour

1. Preserve checkExitPoint and exit-point validation using row.extracted_points. Airport constraints continue to establish whether an exit is permitted for the filed departure.
2. Preserve the existing route-validation algorithm and its use of normalized filed-route tokens built from row.route_points. Exit-point validation separately uses row.extracted_points. The new comparison with the filed route is a warning condition, not a replacement validation algorithm.
3. Retain the existing failure behaviour when no permitted exit point is identified.

### Improve XIT diagnostics

4. Distinguish a known exit point that is invalid for the filed departure from an unknown or unrecognised exit point. Do not describe a known but prohibited point as unknown.
5. Identify alternative departures only where the airport constraints support them, including the applicable points and nopoints constraints. Do not offer unsupported alternatives. Omit alternative-departure advice when none is supported.
6. For the agreed ALOTI example, when the constraints prohibit ALOTI for BPK and support UMLAT and ULTIB, use these messages:

**FULL**

ALOTI is not a permitted exit point for the filed BPK departure. ALOTI is permitted via UMLAT or ULTIB departures.

**SUMMARY**

ALOTI not permitted via BPK

These names describe the agreed example, not a universal airport configuration. Equivalent cases use the actual exit point, filed departure and supported alternatives.

**Project-owner clarification accepted 6 November 2026:** Alternative departures form an unordered list. Their display order does not imply preference or priority. “UMLAT or ULTIB” and “ULTIB or UMLAT” are equivalent for this example. The message wording and supported alternative set remain required; acceptance does not require a particular ordering of that set.

### Warn when a permitted exit is not explicitly filed

7. Generate WRN when the exit point is permitted for the filed departure, appears in EuroScope’s extracted waypoint list, and is absent from the filed route.
8. The exit-point check remains successful in this case. The warning does not become an XIT failure.
9. Use the following messages for ALOTI, substituting the actual exit point in equivalent cases:

**FULL**

ALOTI is a permitted exit point for the filed departure and appears in EuroScope’s extracted waypoint list, but is not explicitly included in the filed route.

**SUMMARY**

ALOTI absent from filed route

10. Do not generate this warning merely because an extracted waypoint exists. The point must be permitted for the filed departure and absent from the filed route.

### Preserve reporting priority and logging boundaries

11. An existing hard failure mnemonic takes precedence over WRN. If another validation check fails while this warning applies, retain the existing failure mnemonic and keep the warning visible under Warnings in Show Checks.
12. Use structured logging to record callsign, departure, exit point, reason for failure or warning, and relevant route information. For the warning, include both the filed route and extracted waypoint representation.
13. Do not introduce additional unsolicited EuroScope console messages.

## Rationale

Extracted waypoints preserve EuroScope’s interpretation of the route and the existing exit-point validation behaviour. A permitted intermediate exit can appear there without being explicitly filed. WRN makes that omission visible without incorrectly classifying it as an exit-point validation failure.

More precise XIT diagnostics explain whether the identified point is known but incompatible with the filed departure. Constraint-supported alternatives are useful only when the available data justifies them. Keeping hard failures ahead of WRN preserves existing reporting priorities while Show Checks retains the warning detail.

## Alternatives considered

- **Validate exits only against the filed route:** Not selected; would change the agreed extracted-waypoint validation behaviour.
- **Treat a permitted extracted-only exit as XIT:** Rejected by the agreed WRN decision; the exit-point check has passed.
- **Log the omission without WRN:** Superseded by the explicit agreement to generate WRN.
- **Offer alternative departures without constraint support:** Not selected; advice must respect points and nopoints.
- **Let WRN replace an existing hard failure mnemonic:** Rejected; the hard failure retains precedence.

## Consequences

Successful exit-point validation can now produce a warning. Consumers of check results must preserve the distinction between a valid exit with a filing omission and an exit-point failure.

Diagnostics need enough constraint context to distinguish known and unknown points and justify alternatives. Warning reporting needs both route representations. Existing route validation remains separate and authoritative for its own checks.

This decision does not prescribe internal data structures, structured log field names, or a new ordering among existing hard failure mnemonics. It does not change controller scope, runway gating or other unrelated validation policies.

## Acceptance criteria

- **AC01:** Existing exit-point and route-validation decisions remain unchanged apart from the specified diagnostics and warning reporting. Verify with SB01, SB02 and SB07.
- **AC02:** Known but prohibited and unknown exit cases are distinguished, with existing failure behaviour retained. Verify with SB03, SB05 and SB07.
- **AC03:** Alternatives respect applicable points and nopoints constraints; unsupported alternatives are absent. Verify with SB03 and SB04.
- **AC04:** The configured ALOTI/BPK case produces the XIT FULL and SUMMARY messages above, with the same wording and supported alternative set. Alternative-departure order is immaterial under the project-owner clarification accepted on 6 November 2026. Verify with SB03.
- **AC05:** A permitted extracted-only ALOTI produces WRN and the exact warning FULL and SUMMARY messages above, while the exit check remains successful. Verify with SB02.
- **AC06:** No new missing-filed-exit warning is emitted when the point is explicitly filed, prohibited, or not identified as permitted. Verify with SB01, SB03, SB05 and SB07.
- **AC07:** A concurrent hard failure retains its mnemonic and the warning remains visible under Warnings in Show Checks. Verify with SB06.
- **AC08:** Failure and warning logs contain the agreed context; warning logs include both route representations. No additional unsolicited EuroScope console messages appear. Verify during SB02 through SB07.

## Sweatbox scenarios

These are planned verification cases, not completed test results. Use controlled constraints and flight plans to establish each precondition.

### SB01 Permitted exit explicitly filed

Use a permitted exit present in both route representations. Expect the existing successful exit-point result, no new missing-filed-exit WRN, and unchanged route validation.

### SB02 Permitted exit present only in extracted waypoints

Use ALOTI permitted for the departure and present in extracted waypoints but absent from the filed route. Include the preceding and following points in the filed route. Expect successful exit validation with WRN, the exact warning messages, Show Checks visibility, and both route representations in the log.

### SB03 Known exit invalid for the filed departure

Configure ALOTI as prohibited via BPK and permitted via UMLAT and ULTIB. Expect XIT with the exact agreed failure messages and no permitted-but-omitted warning.

### SB04 Alternatives limited by constraints

Repeat the known-prohibited case with relevant points and nopoints constraints, including a supported candidate and an excluded candidate. Repeat with no supported alternatives. Expect only supported departures to be recommended and no alternative advice when unsupported.

### SB05 Unknown exit point

Use an exit candidate not recognised by the applicable constraints. Expect existing failure behaviour, an unknown-point explanation distinct from the known-prohibited case, no unsupported alternatives, and no new missing-filed-exit warning.

### SB06 Warning alongside a hard failure

Satisfy SB02 while independently triggering an existing hard validation failure. Expect the existing hard failure mnemonic to retain priority and the warning to remain visible under Warnings in Show Checks.

### SB07 No permitted exit identified

Use a flight plan where no permitted exit is identified by the existing check. Expect existing failure and route-validation behaviour, with no new missing-filed-exit warning.

For failure and warning cases, inspect structured logs and confirm that no additional unsolicited EuroScope console messages are emitted. Record actual results separately during implementation verification.

## Discrepancies

The earlier informational-advisory suggestion in the discussion was superseded by the project owner’s explicit preference for WRN and subsequent agreement. The preceding Application Requirements Document is replaced in purpose by this ADR; the decision content is preserved.

Implementation review found that decision item 2 originally described route validation as using extracted_points, whereas the existing source calls checkRoute with normalized filed-route tokens from row.route_points. checkExitPoint uses row.extracted_points. Both algorithms and inputs were preserved as explicitly required. On 6 November 2026 the project owner explicitly approved correcting this description to match the preserved implementation. Decision item 2 now records the correct inputs. This closes the documentation discrepancy without changing validation behaviour or superseding the decision.
