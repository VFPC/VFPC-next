# ADR-001 — Departure Airport Selection and Validation Scope

> Historical decision: the following policy and implementation observations are retained as recorded. ADR-003 now governs controller scope and UKCP filtering.

- **Decision status:** Superseded by [ADR-003](ADR-003.md) on 2 November 2026
- **Acceptance recorded:** 24 October 2026
- **Implementation status:** Working source contains multi-airport Runway Activity selection; the agreed facility/callsign-specific selection policy is not yet implemented. Multi-airport behaviour has not yet been confirmed through live EuroScope testing.
- **Related record:** [ADR-002](ADR-002.md)

## Context

vFPC needs an explicit policy for determining which departure airports are eligible for validation. Airport selection is distinct from operational controller responsibility: selecting an airport does not establish that the controller currently provides services there.

The handover and development instructions describe an older single-airport architecture. Source inspected during drafting supports multiple Runway Activity departure selections, but applies that selection mechanism universally rather than implementing the accepted facility-specific policy.

## Decision — Agreed and accepted

| EuroScope facility | Airport-selection authority |
|---|---|
| OBS | Departure-active airports from Runway Activity; no assumption of controller responsibility |
| DEL | Single airport identified by controller callsign |
| GND | Single airport identified by controller callsign |
| TWR | Single airport identified by controller callsign |
| APP | Departure-active airports from Runway Activity |
| CTR | Departure-active airports from Runway Activity |
| Unknown facility | Fall back to departure-active airports from Runway Activity |

1. Controller rating must not determine airport selection.
2. For DEL/GND/TWR, Runway Activity is diagnostic. It must not replace or expand the callsign-derived single-airport scope.
3. If the callsign-derived DEL/GND/TWR airport is not departure-active in Runway Activity, produce a configuration warning without excluding that airport from validation. Ordinary validation prerequisites still apply.
4. Handle unrecognised or malformed callsigns safely. Use Runway Activity where the facility policy already specifies it. The fallback for DEL/GND/TWR when no airport can be reliably identified remains unresolved.
5. Support multiple departure airports for facilities using Runway Activity.
6. Departure-list membership must not automatically be interpreted as authoritative controller responsibility.
7. UKCP must not determine or restrict the selected validation scope; see ADR-002.

## Rationale

Facility identifies the type of position being operated. Rating identifies a controller qualification and cannot reliably determine the current position or airport scope.

DEL/GND/TWR positions require predictable single-airport behaviour. A Runway Activity configuration omission should warn the user without disabling otherwise eligible validation.

APP and CTR positions may require several departure airports. OBS and unknown-facility sessions need an explicit selection mechanism without an unsupported inference of responsibility. Runway Activity provides explicit airport selections; it does not prove operational coverage or responsibility.

## Current implementation — Confirmed in working source during drafting

Inspection of `src/analyzeFP.cpp` confirmed:

- `RefreshDepartureAirports_()` collects departure-active sector-file airport elements, normalises their names and stores a sorted, unique set.
- Arrival-active flags are logged but do not add airports to that set.
- `ValidateFlightPlan_()` excludes origins outside that set.
- Snapshots are looked up by flight-plan origin.
- Selection changes trigger revalidation.
- An empty departure selection pauses validation.
- The timer coordinates loading for multiple selected airports.

The agreed facility/callsign-specific selection policy is not yet implemented. The inspected selection path uses multi-airport Runway Activity selection without a facility-based branch or controller-callsign airport resolver. Rating was not used in that path.

These observations describe the working source inspected during drafting, not a release or a complete implementation audit. The multi-airport implementation has not yet been confirmed through live EuroScope testing. These observations do not establish runtime correctness, test coverage or committed implementation. Acceptance of this ADR does not mean that implementation is complete, tested or released.

## Alternatives considered

| Alternative | Assessment |
|---|---|
| Runway Activity for every facility | Matches the inspected selection path but conflicts with DEL/GND/TWR requirements. |
| Callsign-derived airport for every facility | Cannot adequately represent shared approach or en-route positions. |
| Rating-based selection | Rejected: qualification does not determine the position being operated. |
| Observer inference from flight origins | Conflicts with the explicit OBS selection policy. |
| Departure list as responsibility mapping | Rejected as an automatic assumption; list visibility does not establish responsibility. |
| UKCP-controlled airport scope | Rejected by ADR-002. |

## Consequences

- Selection authority must be explicit and facility-dependent.
- DEL/GND/TWR diagnostics must remain separate from eligibility.
- Multi-airport loading and result handling must preserve airport-specific data isolation.
- Changes of facility, callsign or effective airport set must not leave obsolete eligibility or results in use.
- Existing asynchronous loading, immutable snapshots and lightweight callback requirements remain relevant.
- This decision does not choose a cache size, queue design, retry policy or warning interface.

## Outstanding questions — Unresolved

- What validates a callsign prefix as a real airport, including suffixes, aliases and unusual local positions?
- What is the safe fallback for DEL/GND/TWR when callsign-derived airport identification fails?
- How should FSS be classified? It is not explicitly covered by the accepted table.
- How are invalid identity data, unavailable facility data and simulator sessions classified?
- What wording, presentation and repetition policy should be used for ADR-001's configuration warnings? ADR-002 separately accepts UKCP warning content, EuroScope display, logging and avoidance of unchanged duplicate warnings; its exact presentation mechanism remains unresolved.
- What should happen when Runway Activity cannot be read, rather than being successfully read as empty?
- Should the inspected empty-selection pause behaviour be explicitly retained for every Runway Activity-based facility?
- What transition and regression checks are required before declaring this policy implemented?
