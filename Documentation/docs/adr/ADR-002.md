# ADR-002 — UKCP Advisory Validation of Airport Selections

> Historical decision: the following policy and implementation observations are retained as recorded. ADR-003 now governs controller scope and UKCP filtering.

- **Decision status:** Superseded by [ADR-003](ADR-003.md) on 2 November 2026
- **Acceptance recorded:** 24 October 2026
- **Implementation status:** No airport-selection advisory integration identified during drafting; not confirmed implemented or tested
- **Related record:** [ADR-001](ADR-001.md)

## Context

Incorrect airport selections can cause vFPC to validate unintended departures or omit intended departures.

UKCP controller-position data may help identify selections that appear inconsistent with a position's expected coverage. The initial investigation could not retrieve a production payload. A subsequent investigation, reported by the project owner during review, successfully retrieved controller-position records and airport associations from production. Whether those associations definitively represent actual operational responsibility under changing online staffing conditions remains unverified.

Expected coverage, actual responsibility and the airport set selected for vFPC validation are separate concepts.

## Decision — Agreed and accepted

**UKCP controller-position data is an advisory source used to identify potentially incorrect airport selections. It must never determine or restrict which airports vFPC validates.**

The airport-selection rules in ADR-001 remain authoritative.

- A selected departure airport absent from a recognised position's nonempty `top_down` list must produce an advisory warning, as specified below.
- UKCP must not add, remove, replace or filter the effective validation airport set.
- A UKCP mismatch must not prevent validation of an otherwise eligible airport.
- Missing, unavailable or unrecognised UKCP data must not restrict validation.
- A UKCP match must not be presented as proof of actual operational responsibility.

These are consequences of the accepted advisory-only boundary, not claims of implemented behaviour. Acceptance does not certify implementation, testing or API suitability.

## Rationale

UKCP data may reveal likely configuration mistakes while preserving the project's explicit airport-selection policy.

Reference associations may describe normal coverage, coordination relationships or other operational conventions. They must not be assumed to represent current responsibility when positions are split, combined or delegated.

Keeping advisory information separate prevents external availability or mapping errors from becoming validation-scope failures.

## Current implementation and evidence

**Implemented:** No UKCP controller-position airport-selection advisory integration was identified in the source inspected during drafting.

**Existing documentation:** The user guide describes a UK Controller Plugin SRD-search action. That is a separate feature and does not establish controller-to-airport advisory integration.

**Verified investigation evidence:** The subsequent investigation retrieved a production response through the UKCP API documentation interface from:

```http
GET https://ukcp.vatsim.uk/api/controller-positions-v2
```

The endpoint returned HTTP 200 and a JSON array of controller-position records. Verified fields include `callsign`, `top_down`, `frequency`, and departure-release and prenote-related flags. The `top_down` field contains an array of associated airport ICAO codes. Some positions have an empty `top_down` array.

Examples observed in the production response:

| Controller callsign | `top_down` |
|---|---|
| `EGAA_APP` | EGAA, EGAC |
| `SOLENT_APP` | EGHI, EGHH |
| `THAMES_APP` | EGLC, EGKB, EGMC, EGTO |
| `SCO_SOL_CTR` | EGPH, EGPF, EGPK |

These findings establish successful endpoint access, the observed response structure, controller callsigns and airport associations. They are investigation evidence supplied by the project owner, not a guarantee of continued availability or stable API semantics.

**Not yet verified:** Whether `top_down` definitively represents actual operational responsibility as online staffing changes. This evidence does not establish an authoritative live responsibility mapping.

**Historical context:** The initial investigation identified candidate routes from official source but could not retrieve production data, and the original drafting request ended at `/controller-pos`. The subsequent production evidence resolves the endpoint and observed-field uncertainty; it does not resolve live-responsibility semantics or establish a guaranteed API contract.

## Advisory behaviour — Accepted requirements

1. Match the controller callsign against UKCP position data.
2. Where the recognised position has a nonempty `top_down` list, compare departure-active airports with that list.
3. Generate an advisory warning when a selected airport is absent from that list.
4. Identify the controller callsign and unexpected airport in the warning.
5. Explain the mismatch and recommend checking EuroScope Runway Activity.
6. Display the warning in EuroScope and record it in the vFPC log.
7. Avoid repeatedly issuing the same warning when the relevant selection and mapping have not changed.
8. Never prevent constraint loading or flight-plan validation because of a UKCP warning.
9. Never automatically modify EuroScope Runway Activity settings.
10. Treat empty `top_down` arrays as unknown coverage rather than proof of no airport responsibility.
11. Handle unrecognised controller callsigns and UKCP API failures without disrupting validation. Log appropriate diagnostic information.
12. UKCP must never add, remove, filter or otherwise determine the effective validation airport set.

These requirements are accepted, not merely proposed. They do not claim implementation. Resolve the effective validation airport set independently under ADR-001; advisory comparisons do not change it. Warnings identify potentially unexpected selections, not prohibited airports or proven responsibility violations.

The exact EuroScope presentation mechanism, cache lifetime and refresh interval, retry and failure-handling strategy, and the other technical questions below remain unresolved. The requirement to avoid unchanged duplicate warnings is accepted; its implementation is not prescribed here.

## Alternatives considered

| Alternative | Assessment |
|---|---|
| UKCP as an airport allowlist | Rejected: would restrict validation. |
| Automatically correct selections using UKCP | Rejected: would determine validation scope. |
| Block validation until UKCP is available | Rejected: would make advisory data a prerequisite. |
| Omit UKCP advice entirely | Avoids dependency and false warnings but loses a possible configuration aid. |
| Advisory comparison with independently resolved scope | Chosen architectural direction; technical suitability remains to be verified. |

## Consequences

- Scope resolution and advisory assessment must remain separate.
- UKCP failure must not disable validation.
- Advisory warnings must not prevent constraint loading or validation, or automatically change Runway Activity settings.
- Incorrect or stale mappings may create false warnings.
- Users remain responsible for reviewing their configuration; advisory output does not establish operational responsibility.
- UKCP loading must respect existing nonblocking callback requirements.
- This decision accepts an architectural boundary, not an endpoint contract or implementation.

## Outstanding questions — Unresolved

- Do the observed `top_down` airport associations definitively represent actual operational responsibility under changing online staffing conditions, or normal coverage or another relationship?
- How should unusual callsign aliases, legacy callsigns, shared positions, split configurations and changes in online staffing be handled?
- What UKCP cache lifetime and refresh interval should be used?
- What exact mechanism should present warnings in EuroScope? Display in EuroScope and logging are required, but the presentation mechanism is not selected.
- What API retry and failure-handling strategy should be used? Validation must remain unaffected, with appropriate diagnostics.
- How should ADR-001's callsign-derived DEL/GND/TWR scope interact with advisory comparisons of Runway Activity selections?
- What authentication, access and redistribution conditions apply, and what API availability guarantees exist?
- What technical mechanism should suppress duplicate warnings when the relevant selection and mapping have not changed?
